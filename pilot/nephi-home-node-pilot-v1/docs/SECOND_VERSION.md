# JunZan AI 第二版優先事項

本文件記錄第一版正式上線後的第二版優先評估與重構方向。

第一版期間不得因本文件而中斷尼腓的家上線主線，也不得提前進行整套重寫。

## 一、精簡受控架構

第二版優先評估將目前過多、重複的理解與轉換流程逐步合併，目標流程為：

客人訊息與必要上下文
→ AI 理解客人真正要查什麼
→ 系統依 propertyId 查詢正式資料與確定性工具
→ 系統判斷可回答、尚未提供或必須真人處理
→ AI 只使用核准資料組成自然回覆

固定原則：

- 採漸進式重構，不整套重寫。
- 先盤點現有各層的實際責任與依賴，再決定哪些可合併。
- 日期、房況、價格等確定性能力仍由程式工具處理。
- AI 只負責自然語言理解與表達，不得作為業者事實來源。
- 保留 propertyId 業者資料硬隔離。
- 保留正式資料為唯一事實來源。
- 保留「尚未提供」不得視為「沒有」。
- 保留回答規則、禁止承諾與真人轉交判斷。
- 每輪重新查詢目前業者的最新資料。
- 保留可追查的理解結果、資料來源與回答決策紀錄。

## 二、永久可靠性與防退化護欄

第二版必須建立「核心修改不得讓基本回覆能力退化」的永久部署閘門。

每次修改核心流程後，至少自動驗證：

1. 一般知識問題可正常回答。
2. 日期與房況查詢可正常回答。
3. 多輪追問與上下文承接可正常回答。
4. 問題規劃器失敗時可安全降級，不得靜默無回覆。
5. 完整 LINE 處理鏈可產生非空、可送出的回覆內容。

任一項失敗即不得部署。

### 核心失敗不得靜默

凡問題理解、格式驗證、資料查詢、回答控制或自然回覆組成失敗，必須：

記錄失敗階段與內部原因
→ 安全降級
→ 在仍可送出 LINE 回覆時，提供不創造業者事實的安全回覆

不得只標記處理失敗而讓客人完全收不到訊息。

### 新欄位與局部失敗必須安全降級

若新欄位或單一追問細節無法辨識：

- 只降級無效欄位。
- 保留有效的標準主題、其他問題與資料需求。
- 能回答的部分繼續回答。
- 只有缺漏部分補問或轉真人。
- 不得因單一欄位格式錯誤使整則訊息消失。

### 部署驗證不得只看健康網址

健康網址正常只代表服務存活，不能代表 LINE 回覆鏈完整。

核心部署完成前必須驗證：

測試 LINE 事件
→ AI 理解
→ 正式資料查詢
→ 回答規則判斷
→ 自然回覆組成
→ 產生可送出的 LINE 回覆內容

至少涵蓋正常單輪、正常多輪追問與問題規劃器失敗安全降級。

### 快速回退

第二版需建立可驗證的快速回退流程：

- 明確記錄上一個已知可用版本。
- 核心部署後若出現大量無回覆、問題理解連續失敗或 LINE 回覆率異常下降，能迅速退回上一個可用版本。
- 回退前需判斷是否包含資料庫變更或其他不可逆修改。
- 回退後重新驗證健康狀態與完整 LINE 處理鏈。

## 三、執行時機

- 第一版正式上線前：只記錄，不啟動核心架構重構。
- 第一版正式上線後：先盤點、建立新舊流程對照與完整驗收保護，再逐步合併。
- 不得因第二版規劃重新延誤尼腓的家第一版上線。

## 四、LINE 對話訂房確認與自動訊息

第二版評估讓業者在與客人的 LINE 對話中輸入明確訂房確認指令，由系統協助建立結構化訂房紀錄、更新房況，並作為後續住宿階段訊息自動化的可信資料來源。

### 訂房確認流程

1. 業者在與客人的 LINE 對話中輸入明確的訂房確認指令。
2. 系統解析日期、房型、姓名、電話、已收金額、尾款及其他必要訂房資料。
3. 系統向業者顯示解析結果，要求業者再次確認。
4. 只有業者完成再次確認後，系統才能建立訂房紀錄，並將指定日期與房型設為不可售。
5. 後台房況備註顯示簡短訂房摘要，方便業者辨識；備註不得取代底層結構化訂房資料。

客人單方面表示已訂房、已付款或要求保留房間時，不得自動建檔或關房。關房必須來自業者明確指令及再次確認。

### 結構化訂房資料

系統不得只保存一段訂房備註文字。每筆訂房至少必須保存：

- `propertyId`
- LINE `userId`
- 姓名
- 電話
- 入住日
- 退房日
- 房型
- 人數
- 已收金額
- 尾款
- 訂房狀態
- 是否取消或改期
- 各階段訊息是否已傳送

結構化資料是訂房狀態、房況更新、排程與訊息傳送的正式依據。後台顯示的簡短摘要只作為操作介面資訊，不得成為唯一資料來源。

系統不得依賴 LINE 官方帳號後台中由業者替客人修改的顯示名稱或備註，因為這些資料不構成穩定、可驗證的訂房識別與狀態來源。

### 自動訊息與排程

未來以結構化訂房資料支援業者設定的階段訊息，包括：

- 入住前一天
- 入住當天
- 入住期間
- 退房後

排程執行前必須重新確認訂房狀態、入住與退房日期，以及該階段訊息是否已傳送。已取消、已改期或不符合當前階段的訂房不得沿用舊排程傳送訊息。

### 一致性、安全與隔離

- 必須以可重入與去重機制避免同一筆訂房重複建檔。
- 必須避免同一確認動作重複關房。
- 必須避免同一住宿階段訊息重複發送。
- 訂房、房況、備註、排程及訊息傳送狀態都必須維持 `propertyId` 硬隔離。
- 不得因 LINE event 重送、業者重複確認、服務重啟或排程重試而破壞資料一致性。
- 取消或改期必須更新結構化訂房狀態及相關排程；不得只修改顯示備註。

### 執行邊界

此功能目前只記錄於第二版規劃，不得在第一版期間實作，也不得因此修改或延誤第一版上線流程。

## 五、AI 網址匯入與業者快速上架

第二版需評估並建立「業者貼上公開網址，JunZan AI 協助產生初始資料草稿」的快速上架流程，降低新業者第一次導入時的填寫負擔。

第一個可交付版本聚焦：

公開民宿官網或公開訂房頁網址
→ 系統抓取可公開讀取的內容
→ 優先解析網頁結構化資料與明確文字
→ AI 整理成符合 JunZan AI schema 的草稿
→ 業者逐項確認、修改或略過
→ 只有確認後才寫入正式 Property Facts

合理目標是將原本約 20～30 分鐘的初始填寫，縮短為約 5～10 分鐘的確認與補充；不得以未經驗證的「全自動完成」作為第一階段目標。

### 第一階段可匯入欄位

優先評估支援：

- 民宿名稱
- 地址
- 電話
- Email
- Google Maps 網址
- LINE 官方帳號連結
- 入住時間
- 退房時間
- 停車資訊
- 烤肉規則
- 戲水池或游泳池
- 早餐資訊
- 寵物規則
- 付款方式
- 訂金規則
- 取消與延期規則
- 入住方式
- 住宿規則
- 房型正式名稱
- 房型可住人數
- 網站明確公開的房型價格

系統不得因網站未提供某欄位，就自行推論成「沒有」。未找到的欄位必須標示為待業者補充。

### 每個欄位的可追查資料

每一個 AI 產生的候選欄位至少需保留：

- 候選值
- 來源網址
- 來源頁面或區塊
- 支持該值的來源原文
- 信心程度
- 尚未確認、已確認、已修改或已略過的狀態

例如網站只寫「平日 2,200 元起」時，不得直接推定為所有週一至週四固定 2,200 元。這類資料應以低信心候選值呈現，要求業者確認或補充適用條件。

### 正式資料寫入邊界

- AI 匯入結果只能先建立草稿，不得直接覆蓋正式 Property Facts。
- 業者必須能逐項確認、修改、拒絕或保留空白。
- 只有業者明確確認的資料才能進入正式資料來源。
- 已有正式資料時，預設不得被新抓取內容靜默覆蓋。
- 套用前必須清楚顯示新增、變更與衝突內容。
- 匯入、草稿、確認與正式寫入都必須維持 propertyId 硬隔離。

### 抓取與來源優先順序

系統應優先採用較可信且可追查的來源：

1. 網頁內的 JSON-LD、Schema.org 或其他結構化資料。
2. 明確標示的基本資料、房型、FAQ、交通、政策與價格文字。
3. 普通 HTML 中可辨識的公開內容。
4. 必要時才使用受控瀏覽器處理 JavaScript 動態載入頁面。
5. 最後才由 AI 對候選內容進行分類與結構化，不得讓 AI 憑空補值。

### 外部平台與授權限制

- 不得繞過登入、驗證碼、付費牆或其他存取限制。
- 不得假裝擁有 Agoda、Booking.com、Airbnb、PMS 或 Channel Manager 的資料存取權。
- 需要登入的平台資料，應優先使用官方 API、合作授權、iCal、業者匯出檔或業者明確授權的連線方式。
- 即時房況、訂單、取消與價格同步不得只靠一般網頁抓取。
- 抓取公開網站時仍需遵守適用的網站條款、robots 規範及合理的流量限制。

### 使用者介面方向

匯入後至少分成三類顯示：

- 已找到，請確認
- 可能找到，但需要確認
- 網站未提供，請補填

業者應能快速完成：

- 全部接受明確且高信心的欄位
- 單欄修改
- 查看來源原文
- 拒絕錯誤候選值
- 暫時略過非必要欄位

不得把傳統長表單原封不動再加一層 AI；目標是讓業者主要進行確認與補缺，而不是重新輸入已經存在於公開網站上的資料。

### 後續擴充方向

第一階段穩定後再評估：

- 多頁網站自動探索
- 房型照片與房型正確配對
- 複製既有房型設定
- 從業者提供的 PDF、試算表或匯出檔匯入
- 經正式授權的 PMS、OTA 或 Channel Manager 串接
- AI 對話式補齊缺漏欄位
- 定期偵測公開網站資料變更，但仍須由業者確認後才能套用

### 執行邊界

此功能只記錄於第二版規劃。第一版正式上線前不得開始實作、不得修改目前 onboarding 主流程，也不得因此延誤尼腓的家第一版上線。

## 六、Planner 職責收斂與受控核心責任移轉

第二版不刪除 Planner，也不以整套重寫取代第一版。Planner 保留，但職責收斂為「理解候選產生器」；所有會影響正式資料查詢、狀態與對客決策的結果，必須由受控核心最終確認。

### Planner 保留的職責

- 自然語言理解
- 上下文理解
- 多問題拆解候選
- 原始實體文字抽取
- 原始日期語句抽取
- 主題候選
- 細節意圖候選
- 模糊與風險候選
- 置信度與原始語句證據

### Planner 不再最終決定的事項

- 最終標準主題
- 最終 task 類型
- 最終細節意圖
- 最終 `requestedOutputs`
- state 的 set／replace／clear／keep
- 正式入住日、退房日與晚數
- 工具選擇
- 正式資料查詢
- 回答、補問或轉真人

### 第二版正式流程

客人訊息
→ AI 理解問題與上下文
→ 產生受控的資料需求候選
→ 受控核心確認正式資料需求
→ 系統選擇確定性工具
→ 系統依 `propertyId` 查詢正式資料
→ 系統產生可說、不可說、需確認的核准材料
→ AI 只使用核准材料自然回答

### 責任移轉對照表

| 項目 | 第一版目前由誰決定 | 第二版最終決定元件 | 遷移風險 | 測試與回退方式 |
| --- | --- | --- | --- | --- |
| `canonicalCandidate` | Planner 提出，部分由語意契約與 Entity Resolver 修正或確認 | 受控資料需求契約加 property-scoped Entity Resolver | 錯誤主題可能查到錯誤能力或轉真人 | 影子比對 canonical 結果；異常時維持第一版結果 |
| `detailIntent` | Planner 產生，第一版語意契約只攔截部分矛盾 | 受控資料需求契約依候選與可追溯語意證據確認 | 基礎詢問被錯當資格或細節問題 | 真實錯誤形狀黃金測試；異常時回到第一版契約 |
| `requestedOutputs` | Planner 產生，語意契約有限修正 | 由正式 task、canonical topic 與 detail intent 確定性衍生 | 兩個錯誤欄位可能互相證明 | 契約組合矩陣；不一致即拒絕第二版結果 |

| 回答／補問／轉真人 | Executor 結果與 Response Plan 決定，Planner 另輸出部分安全候選 | Policy／Response Plan 依核准材料最終決定 | 局部未知擴大成整輪 fallback | 多問題 coverage 與 Unknown 契約；異常時使用第一版受控回覆 |

### 標準資料需求契約

第二版需定義精簡、受控且可驗證的資料需求格式。AI 只需輸出：

- 客人在問哪些問題
- 每個問題的原始語句
- 提到哪些條件
- 提到哪些日期文字
- 提到哪些人數、房型或地點
- 問題之間的上下文關係
- 模糊或需要確認的部分

不得要求 AI 自由產生完整執行組合。正式 task、狀態操作、工具、查詢參數與回答決策都必須由受控核心從候選資料衍生。

### 新舊流程影子比對

第二版新流程不得直接取代第一版。導入時先建立影子模式：

- 第一版照常回覆客人。
- 第二版只在背景執行。
- 比較兩者的資料需求、查詢結果與核准材料。
- 第二版結果不得直接送給客人。
- 只有影子比對穩定通過，且差異已有可追查證據後，才逐步切換。

### 真實訊息黃金測試集

將真實 LINE 問題與曾經失敗的案例保存為永久測試集，至少包含：

- 位置
- 房況
- 設施
- 政策
- 多問題
- 多輪追問
- 錯字
- 相對日期
- Planner 格式合法但語意錯誤

每次修改核心都必須執行完整黃金測試集；人工正確 plan、stub response 或局部 runner 不得取代真實錯誤形狀與完整鏈驗證。

### 快速回退

第二版必須明確記錄並驗證：

- 第一版最後已知正常版本
- 第二版功能開關
- 新流程異常時如何立即切回第一版
- 資料庫變更是否可逆
- 回退後必須重跑哪些真實驗收

任何新流程若造成無回覆、事實錯誤、跨 property 污染、多問題漏答或 Unknown 被回答成 No，必須停止切換並回到最後已知正常的第一版路徑。

### 本次永久教訓

- Planner 責任過多會產生格式合法但語意錯誤的欄位組合。
- 結構驗證不能取代語意契約。
- 人工正確 plan 與 stub 測試不能證明真實模型穩定。
- 核心修改必須以真實錯誤形狀建立契約測試。
- 第一版只補安全契約，不提前重分配整套責任。
- 第二版才逐步重新分配責任。
- 不整套重寫，採漸進式移轉並保留可驗證回退。
